# GPU Kernel IR to Metal Source

`exportMetalKernel(module)` converts the restricted GPU kernel generated by [TensorMap GPU lowering](gpu-kernel-lowering.md) into Metal Shading Language. The implementation is ordinary C++ and uses no Metal or Foundation APIs.

The public interface is in [MetalExporter.h](../src/conversion/MetalExporter.h):

```cpp
struct MetalKernelSource {
  std::string source;
  std::string entrypoint;
  std::size_t inputCount;
};
mlir::FailureOr<MetalKernelSource> exportMetalKernel(mlir::ModuleOp module);
```

On success the returned strings own their data and do not depend on the MLIRContext remaining alive. The input module is not modified. On failure the exporter emits MLIR diagnostics identifying the stage, operation, and reason, and returns no source object.

## Validation before emission

The exporter first runs the MLIR verifier and checks the complete supported structure. Only then does it generate source. It does not attempt to export arbitrary GPU programs or to guess the meaning of unsupported operations.

Supported input consists of exactly one `gpu.module` with one defined `gpu.func` kernel. Its arguments are 1-3 dynamic identity-layout rank-1 i32 input memrefs, one output of the same device type, and an i32 count. Results and workgroup/private memory attributions are unsupported.

The entry block must contain the F2 linear-index envelope: x block ID, block dimension and thread ID, index multiplication/addition, unsigned count-to-index conversion, unsigned less-than comparison, a result-free bounds guard without an else branch, and a void return. Equivalent but differently ordered or optimized envelopes are currently rejected; this is intentionally a small exporter contract.

Inside the guard, the first K operations load each input at `index`, in parameter order, and the last write stores a local scalar result to `output[index]`. Between them, the exporter accepts only i32 integer constants and wrapping add/subtract/multiply. Operands must refer to the loaded element or earlier scalar results. No-wrap promises, captured count values inside scalar computation, other types, arbitrary casts/control flow, extra memory accesses, and incompatible indexing are rejected.

## SSA values become temporaries

Operations are emitted in their existing order. Each result gets one local name, such as `v7` or `v8`. A value-to-name table records these names for later operands.

For example, a shared square becomes:

```metal
const uint v8 = v7 * v7;
const uint v9 = v8 + v8;
```

The square is defined once and referenced twice; the exporter does not recursively expand it into two expressions. Source SSA names are not copied into Metal identifiers.

## Integer and launch contract

Buffers use `device const uint*` and `device uint*`, and all scalar/index arithmetic uses uint. Constants are emitted as their unsigned 32-bit bit patterns with a `u` suffix: -1 becomes `4294967295u`, INT_MIN becomes `2147483648u`, and INT_MAX becomes `2147483647u`. Integer arithmetic therefore retains the intended modulo-2^32 behavior. The bounds predicate uses bool.

The emitted entrypoint is always `tensor_map`, independent of the input GPU function's symbol name. The result explicitly returns that name. For K inputs, bindings are inputs at buffer(0..K-1), output at buffer(K), and a uint count at buffer(K+1). `inputCount` records validated K for runtime arity checking; K=1 preserves original shader text and bindings.

The index formula uses `threadgroup_position_in_grid.x * threads_per_threadgroup.x + thread_position_in_threadgroup.x`. A launcher must:

- Use a one-dimensional grid and uniform one-dimensional threadgroups, padding the last group and relying on the generated bounds guard.
- Check count, buffer capacities, separate input/output allocations, and the u32 range of padded indices before execution.
- Avoid nonuniform final groups whose actual width could change the meaning of `block_id * block_dim`.

MLIR index width is target-dependent. This exporter accepts the validated F2 pattern under the above u32 launch contract; it is not a general index-width lowering. The [Metal runtime](metal-runtime.md) implements these launch and capacity checks.

## Tests

Exporter cases now run through the [unified data runner](testing.md). The [shared-square case](../test/metal_exporter/shared_square.mlir) contains GPU IR, a complete expected shader, preservation assertions and a device-compilation run in one file. The [integer-bit case](../test/metal_exporter/integer_bits.mlir) similarly checks the complete MSL for negative/extreme constants and all three arithmetic operators.

```sh
cmake --build build --target tester tensor_interfaces metal_runtime_checks metal_stub_checks cpu_input_contracts gpu_input_contracts gpu_input_stub_contracts -j3
./build/tester --suite test/metal_exporter --no-metal
./build/tester --suite test/metal_exporter --run compile --require-metal
```

Each negative case contains the actual unsupported IR plus expected stage/op/message. The runner validates before export, applies full golden or FileCheck assertions, and invokes a thin Apple adapter for metal-compile. That adapter compiles the generated source and creates a compute pipeline in memory; it does not maintain its own fixture list or dispatch kernels. No device produces a per-run skip unless strict mode is requested.

SconeMLMetalExporter is still ordinary C++ with no device API calls. The two remaining C++ interface tests check frontend linkage and rejection of malformed in-memory IR; all program-based exporter tests are data files. Both generated shaders compiled and produced pipelines locally during F3 validation.

## Execution status

The public GPU runner now extracts GPU IR, invokes this exporter, and passes the returned source and entrypoint to the one-shot Metal runtime. The recursive expression emitter has been removed. The `tensor-metal` test pipeline checks actual dispatch and numeric results; `metal-compile` continues to check compilation/pipeline creation only. See [runtime integration](metal-runtime.md) for launch geometry, bounds, and device validation commands.

M2-C cases in `test/multi_input/ir` include a complete three-input expected MSL, ordered loads/SSA checks and rejection of swapped input loads. See [multi-input details](multi-input-tensor-map.md).
