# GPU Kernel IR to Metal Source

`exportMetalKernel(module)` converts the restricted GPU kernel generated by [TensorMap GPU lowering](gpu-kernel-lowering.md) into Metal Shading Language. The implementation is ordinary C++ and uses no Metal or Foundation APIs.

The public interface is in [MetalExporter.h](../src/conversion/MetalExporter.h):

```cpp
struct MetalKernelSource {
  std::string source;
  std::string entrypoint;
};
mlir::FailureOr<MetalKernelSource> exportMetalKernel(mlir::ModuleOp module);
```

On success the returned strings own their data and do not depend on the MLIRContext remaining alive. The input module is not modified. On failure the exporter emits MLIR diagnostics identifying the stage, operation, and reason, and returns no source object.

## Validation before emission

The exporter first runs the MLIR verifier and checks the complete supported structure. Only then does it generate source. It does not attempt to export arbitrary GPU programs or to guess the meaning of unsupported operations.

Supported input consists of exactly one `gpu.module` with one defined `gpu.func` kernel. Its arguments are two dynamic, identity-layout, rank-1 i32 memrefs in GPU global address space, followed by an i32 count. Results and workgroup/private memory attributions are unsupported.

The entry block must contain the F2 linear-index envelope: x block ID, block dimension and thread ID, index multiplication/addition, unsigned count-to-index conversion, unsigned less-than comparison, a result-free bounds guard without an else branch, and a void return. Equivalent but differently ordered or optimized envelopes are currently rejected; this is intentionally a small exporter contract.

Inside the guard, the first operation loads `input[index]` and the last write stores a local scalar result to `output[index]`. Between them, the exporter accepts only i32 integer constants and wrapping add/subtract/multiply. Operands must refer to the loaded element or earlier scalar results. No-wrap promises, captured count values inside scalar computation, other types, arbitrary casts/control flow, extra memory accesses, and incompatible indexing are rejected.

## SSA values become temporaries

Operations are emitted in their existing order. Each result gets one local name, such as `v7` or `v8`. A value-to-name table records these names for later operands.

For example, a shared square becomes:

```metal
const uint v8 = v7 * v7;
const uint v9 = v8 + v8;
```

The square is defined once and referenced twice; the exporter does not recursively expand it into two expressions. Source SSA names are not copied into Metal identifiers.

## Integer and launch contract

Buffers use `device const uint*` and `device uint*`, and all scalar/index arithmetic uses uint. Constants are emitted as their unsigned 32-bit bit patterns with a `u` suffix: -1 becomes `4294967295u`, INT_MIN becomes `2147483648u`, and INT_MAX becomes `2147483647u`. Integer arithmetic therefore retains the intended modulo-2^32 behavior. The bounds predicate uses bool.

The emitted entrypoint is always `tensor_map`, independent of the input GPU function's symbol name. The result explicitly returns that name. Bindings are input at buffer(0), output at buffer(1), and a uint count at buffer(2).

The index formula uses `threadgroup_position_in_grid.x * threads_per_threadgroup.x + thread_position_in_threadgroup.x`. A launcher must:

- Use a one-dimensional grid and uniform one-dimensional threadgroups, padding the last group and relying on the generated bounds guard.
- Check count, buffer capacities, separate input/output allocations, and the u32 range of padded indices before execution.
- Avoid nonuniform final groups whose actual width could change the meaning of `block_id * block_dim`.

MLIR index width is target-dependent. This exporter accepts the validated F2 pattern under the above u32 launch contract; it is not a general index-width lowering. Runtime checks and dispatch integration remain subsequent work.

## Tests

The `SconeMLMetalExporter` library and `metal_exporter` executable are ordinary C++ targets. They do not link a device runtime. The golden [MSL fixture](../test/metal_exporter/shared_square.metal) asserts the complete generated shader, including shared temporaries and guard placement. Additional tests cover integer bit patterns, source immutability, malformed IR, and diagnostic rejection of unsupported signatures, layouts, operations, predicates, dimensions and scalar dependencies.

The existing GPU-lowering test also calls the exporter on its generated kernels, including frontend polynomial, subtraction and identity maps, so the two APIs are checked together.

On Apple, `metal_exporter_compile` is a separate Objective-C++ executable. It reads generated shaders, compiles them on the available Metal device and creates compute pipelines for the returned entrypoint convention. It does not dispatch them. CTest fixtures ensure generation succeeds before compilation runs; no device produces an explicit skip, not a compilation success.

```sh
cmake -S . -B build
cmake --build build --target metal_exporter tensor_gpu_lowering -j3
ctest --test-dir build -R '^(metal_exporter|tensor_gpu_lowering)$' --output-on-failure
```

On Apple, additionally run:

```sh
cmake --build build --target metal_exporter_compile -j3
ctest --test-dir build -R '^metal_exporter_compile$' --output-on-failure
```

Generated `.metal` files live in `build/exported-msl/`. The `shared.metal` case tests shared computation; `integer.metal` covers negative/extreme constants and all three arithmetic operators. Both compiled and produced pipelines locally during F3 validation. CI can skip device compilation when no Metal device is available.

## Execution status

This completes source generation and compilation validation. The public GPU runner still uses its original expression-to-MSL path. Connecting the new exporter, checking dispatch dimensions and using the uniform launch contract belong to F4; successful pipeline creation is not proof of kernel execution or numeric results.
